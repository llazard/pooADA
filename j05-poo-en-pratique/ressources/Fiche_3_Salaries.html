Exercice 3 : les salariés

Le contexte : le service RH calcule la paie. Un salaire de base pour tous, une prime pour le manager, la moitié pour le stagiaire : le commun s'écrit une fois.

Ce qui est travaillé : une classe mère abstraite, extends et super(...), la redéfinition avec @Override et super., et une boucle sur le type parent.

Question 0, avec la formatrice

Copiez les classes et le Main, et lancez le.

public abstract class Employee {
    private final String name;
    private final int baseSalary;
    public Employee(String name, int baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }
    public String getName() { return name; }
    public int getBaseSalary() { return baseSalary; }
    // Le salaire versé : par défaut, le salaire de base.
    public int getSalary() { return baseSalary; }
    public String getInformation() {
        return name + " : " + getSalary() + " €";
    }
}
public class Developer extends Employee {
    public Developer(String name, int baseSalary) {
        super(name, baseSalary);
    }
}
Employee alice = new Developer("Alice", 2500);
System.out.println(alice.getInformation());

La consigne

  1. Créez Manager, qui hérite de Employee, avec une prime. Dans Manager, écrivez une méthode getSalary() annotée @Override : elle redéfinit celle de Employee, et renvoie le salaire de base plus la prime.
  2. Créez Intern, un stagiaire, et redéfinissez aussi getSalary() : elle renvoie la moitié du salaire de base.
  3. Dans le Main, une List<Employee> : Alice, développeuse à 2500 € ; Bob, manager à 3000 € avec 500 € de prime ; Chloé, stagiaire à 1600 €. Une seule boucle affiche chaque salarié, puis la masse salariale : 6800 €.

Astuce : dans une classe fille, super.getSalary() appelle la version de la méthode écrite dans la mère. Le manager reprend le salaire de base calculé par Employee, sans le recalculer, et n'y ajoute que sa prime.

reflexion.md :

  • Employee est abstraite. Essayez new Employee("Bob", 3000) : que dit le compilateur ? Pourquoi peut-on créer un Developer, qui ne redéfinit pourtant rien ?
  • Le constructeur de Manager commence par super(name, baseSalary). Retirez cette ligne : que se passe-t-il ? Pourquoi ?
  • Dans le getSalary() de Manager, remplacez super.getSalary() par getSalary(), et lancez. Que se passe-t-il ? Pourquoi faut-il super. ?
  • Votre List<Employee> contient un Developer, un Manager et un Intern : trois classes différentes. Pourquoi Java accepte-t-il de les mettre dans la même liste ?
  • getInformation() n'est écrite que dans Employee, qui ne connaît pas la prime. Pourquoi affiche-t-elle pourtant 3500 € pour Bob ?
  • Dans l'exercice 1, chaque héros écrivait son propre getName(), ligne pour ligne la même. Ici, Developer, Manager et Intern n'écrivent ni getName() ni getInformation(), et pourtant ils les ont. Pourquoi ? Qu'est-ce que l'héritage permet, que l'interface ne permettait pas ?

Étape 2 : à quoi sert @Override ?

@Override est facultatif : le code compile aussi sans. Voyons ce qu'il apporte. Dans Manager, faites une faute de frappe : renommez getSalary() en getSallary(), et lancez. Lisez le message.

Retirez maintenant @Override de cette méthode, et relancez : combien touche Bob, et quelle est la masse salariale ? Remettez ensuite le bon nom et l'annotation.

reflexion.md :

  • Avec la faute de frappe, que s'est-il passé avec @Override, puis sans ? À quoi sert @Override ?

Étape 3 : le type déclaré

Ajoutez dans Manager une méthode getBonus(), qui renvoie la prime. Dans le Main, écrivez Employee e = new Manager("Bob", 3000, 500);, puis essayez System.out.println(e.getSalary()); et System.out.println(e.getBonus());.

reflexion.md :

  • e contient un manager, qui a bien une prime. Pourquoi e.getSalary() renvoie-t-il 3500, alors que e.getBonus() ne compile pas ?

Partie optionnelle

Un freelance est payé à la journée : 400 € par jour, pendant 5 jours. Créez Freelance, qui hérite de Employee avec un salaire de base à 0, et ajoutez-le à la liste : la boucle ne change pas. Mais un freelance est-il vraiment un Employee ? À explorer : « composition over inheritance ».
